# ReForge AI — Implementation Tasks

Goal: (1) allow optional known dimensions on the upload page to make 3D renders more accurate, and (2) stop hardcoding part types so any component (helical gear, valve, bolt, etc.) can be reconstructed instead of always rendering a spur gear.

Approach decided: generic **geometry recipe engine** generated by Gemini, executed by a generic Three.js builder, with the existing 6 parametric builders kept as a fallback so nothing regresses. Helical teeth built via a **stacked-slice approximation** (works on three.js 0.128, no new dependencies).

**Status:** T1–T10 implemented and verified (build passes, servers start, headless smoke tests pass). Workstream 3 (below) addresses gear accuracy + cogwheel/bevel/worm support.

## Workstream 2 — Any part type (generic recipe engine)

### T4 · Backend: free `componentType` + `geometryRecipe` schema (+ ANALYSIS_SCHEMA mirror)
**File:** `backend/gemini.js`

- Change `componentType` from the closed enum to a free `STRING`.
- Add `geometryRecipe` object with:
  - `style`: enum `["revolved", "extruded", "gear", "combination"]`
  - `revolvedProfile`: array of `{ z, radius }` (meridian profile, sorted by z)
  - `outline`: array of `{ x, y }` (closed 2D polygon for extruded parts)
  - `holes`: array of `{ cx, cy, radius }` (through-holes in the extruded face)
  - `depth`: extruded depth
  - `gear`: `{ teeth, module, pressureAngle, helixAngle, faceWidth, boreRadius }`
  - `primitives`: array of additive shapes `{ kind: "box"|"cylinder"|"sphere"|"cone"|"torus", ...sizes, position: {x,y,z}, rotation: {x,y,z} }`
- Add top-level `module` and `helixAngle` fields alongside existing `teeth`.
- **CRITICAL — mirror the full `geometryRecipe` shape into `ANALYSIS_SCHEMA` itself.** `ANALYSIS_SCHEMA` is used on the retry path in `analyzeComponent` (`responseSchema: ANALYSIS_SCHEMA` when the free-form JSON parse fails). Schema-constrained generation only emits fields defined in the schema — if `geometryRecipe` (and `module`/`helixAngle`) are not added to `ANALYSIS_SCHEMA`, the retry path silently returns a response *without* a recipe, breaking the entire feature on the very path meant to be the safe fallback.
- Extend `normalizeAnalysis` to sanitize the recipe:
  - Numbers must be finite and positive; teeth clamped to ≥ 6.
  - **Bounded/clamped, not just "positive finite".** A hallucinated `radius: 50000` or a 10,000-point outline would freeze or degenerate the renderer. Apply hard caps:
    - `revolvedProfile` ≤ 200 points
    - `outline` ≤ 200 points
    - `holes` ≤ 50
    - `primitives` ≤ 30
  - **Dimension-ratio clamp:** reject or clip any value that exceeds 1000× the median recipe dimension, so one bad number can't dominate the mesh.
  - Recipe set to `null`/empty when unusable (violates any cap → entire recipe invalid → fallback path).

### T5 · Backend: prompt instructs recipe generation
**File:** `backend/gemini.js` (`analysisPrompt`)

- Instruct Gemini to classify freely (no forced list) and emit a `geometryRecipe` consistent with the measured dimensions (all in mm).
- Guidance per style:
  - axisymmetric/rotational parts → `revolved` profile
  - plates, brackets, housings → `extruded` outline + holes
  - toothed wheels → `gear` (spur = helixAngle 0, helical = helixAngle > 0)
  - ambiguous/complex → `combination` of simple primitives
- Leave unknowns as null rather than guessing wrong numbers.

### T6 · Frontend: recipe sanitizer + generic builders
**File (new):** `frontend/src/lib/recipe.js`

- `sanitizeRecipe(analysis)` → normalized, clamped recipe object (apply the same caps as T4 client-side), or `null` if unusable.
- Generic builders (reuse existing materials from `reconstruct.js`):
  - `buildLathe(profile)` → `LatheGeometry` from `[{z, radius}]`. **Constraint:** `LatheGeometry` revolves around the Y axis and requires all radius (x) values ≥ 0 with points ordered monotonically along the axis — the sanitizer must clamp negative radii to 0 (not reject) and sort by z so `LatheGeometry` doesn't choke.
  - `buildExtruded(outline, holes, depth)` → `ExtrudeGeometry`. **Not a data pass-through:** `outline` point arrays must be converted into a `THREE.Shape` via `moveTo`/`lineTo` (use `absarc` for circular profiles), and each `hole` must be a `THREE.Path` pushed into `shape.holes`. Winding order matters — holes must wind opposite to the outline (e.g. `absarc(..., true)` for holes) or they won't subtract.
  - `buildGearFromRecipe(gear)` → **scope note:** for v1 this **reuses the existing trapezoidal tooth approximation** from `gearShape()` in `reconstruct.js`, parameterized by `module`/`pressureAngle`/`helixAngle` — it does NOT implement a true involute curve (that is new trig/curve math and is tracked as a separate follow-up, see Notes). Add bore + hub styling, and **helical via stacked slices**: N≈24 thin straight-tooth extrusions, each progressively rotated by `helixAngle / N`. Works on three.js 0.128.
  - `buildPrimitives(primitives)` → additive box/cylinder/sphere/cone/torus meshes with position/rotation.
  - `executeRecipe(recipe)` → assembles a `THREE.Group`.

### T7 · Frontend: normalize recipe-built geometry to viewport size
**File:** `frontend/src/lib/recipe.js` (`executeRecipe`)

- `computeParams()` today normalizes render size via `scale = 6 / maxDim` so a 20 mm bolt and a 400 mm flange both render at a sane viewport size. The recipe path builds from raw mm values with no equivalent step — a recipe-rendered part could come out tiny or huge depending on real-world size.
- **After `executeRecipe` builds the group, compute its bounding box (`Box3.setFromObject`) and scale the whole group by `6 / maxDimOfBox` so recipe and fallback paths are consistent in the viewport.** Center the group too. Apply the same scaling to the fallback label/params path so both render at the same nominal size.

### T8 · Frontend: wire `buildModel` to recipe-first, fallback-second
**File:** `frontend/src/lib/reconstruct.js`

- `buildModel(analysis)`: if `sanitizeRecipe(analysis)` returns a valid recipe → `executeRecipe` (T6/T7); otherwise fall back to the existing 6-builder `switch` (no regression).
- Keep `castShadow` traversal, params, and label in both paths.
- Fix `resolveComponentType`/labels: when a recipe renders the part, use `analysis.componentType` verbatim for the label (no forced "spur gear" mapping). Keep existing fuzzy classification only for the fallback path.

### T9 · Frontend: workbench extras
**Files:** `frontend/src/main.jsx`, `frontend/src/lib/reconstruct.js` (`dimensionList`)

- Show `module` and `helixAngle` in the dimensions overlay when present.
- Workbench status label reflects the free-form `componentType`.

## Workstream 3 — Gear accuracy & advanced gear types

Problem reported: a photo-only **spur gear / cogwheel** renders with wrong teeth count, wrong proportions, and/or wrong style. Helical gears are correct *only when* the user supplies measurements. Gemini's conservative "prefer null" instruction plus a non-mandatory gear style line produces low-quality gear recipes. Additional gaps: cogwheels need **lightening holes**, and **bevel** and **worm** gears are unsupported.

### T11 · Backend: harden the gear prompt
**File:** `backend/gemini.js` (`analysisPrompt`)

- Replace the single gear bullet with a mandatory **CRITICAL GEAR RULES** block:
  - If the part has ANY teeth (gear, sprocket, cogwheel, ratchet, bevel gear, worm gear) → MUST use style `"gear"`. Never `revolved`/`extruded`/`combination` for a toothed part.
  - When style is `gear`, fill ALL gear fields by estimating from the images — do NOT leave them null:
    - `teeth`: count visible teeth and extrapolate around the circumference.
    - `module`: if outerDiameter and teeth are estimated, `module ≈ outerDiameter / (teeth + 2)`.
    - `helixAngle`: 0 for spur, estimated degrees for helical.
    - `faceWidth`: tooth face thickness from the side view.
    - `boreRadius`: central hole radius from the photo.
  - Mirror `teeth`/`module`/`helixAngle` into the top-level fields too.
- Supersede the global "Prefer leaving a value as null" line **for gear fields** — estimates are required there.

### T12 · Frontend: recipe builder falls back to analysis dimensions
**File:** `frontend/src/lib/recipe.js` (`buildGearFromRecipe`, `executeRecipe`)

- Thread the `analysis` object into `buildGearFromRecipe` (via `executeRecipe` → `sanitizeRecipe` already has it).
- When `gear.module` is missing but `analysis.dimensions.outerDiameter` exists:
  - `outerR = outerDiameter / 2`
  - `module = outerDiameter / (teeth + 2)` (standard gear formula)
  - `toothHeight = 2.25 * module`
- When `gear.faceWidth` missing → use `analysis.dimensions.height` or `thickness`.
- When `gear.boreRadius` missing → use `analysis.dimensions.innerDiameter / 2`.
- Keeps the hardcoded `outerR = 2.8` only as a last resort (no dims at all).

### T13 · Backend: cogwheel lightening holes (schema + sanitize + prompt)
**File:** `backend/gemini.js`

- Add `gear.lighteningHoles: [{ cx, cy, radius }]` to `ANALYSIS_SCHEMA` (mirror — retry path must keep it).
- Extend `sanitizeRecipe`: sanitize lightening holes (finite positive radius, ≤ 50 holes, clipped like other dims).
- Prompt: "If the gear has holes between hub and rim (cogwheel web/lightening pattern), provide them as `[{cx, cy, radius}]` in mm centered on the gear axis."

### T14 · Frontend: render lightening holes
**Files:** `frontend/src/lib/geo.js` (`gearShape`), `frontend/src/lib/recipe.js` (`buildGearFromRecipe`)

- `gearShape(teeth, outerR, toothHeight, boreR, lighteningHoles = [])` — add each hole as a `THREE.Path.absarc` (clockwise winding) pushed into `shape.holes`.
- `buildGearFromRecipe` passes `recipe.gear.lighteningHoles` through for both spur and helical paths.

### T15 · Backend: bevel gear support (schema + sanitize + prompt)
**File:** `backend/gemini.js`

- Add `gear.gearType: enum ["spur", "helical", "bevel", "worm"]` and `gear.coneAngle: NUMBER` (half-angle of the pitch cone, degrees) to `ANALYSIS_SCHEMA` (mirror).
- Extend `sanitizeRecipe` for the new fields (gearType validated against enum, coneAngle finite 0–90).
- Prompt: add "bevel gear" to classification examples; "set gearType 'bevel' and provide coneAngle (standard miter gears ≈ 45°)."

### T16 · Frontend: buildBevelGear
**File:** `frontend/src/lib/recipe.js`

- New `buildBevelGear(gear)` builder — tapered tooth loft:
  - Large-end pitch radius `pitchR_large = (teeth * module) / 2`; small-end `pitchR_small = pitchR_large * cos(coneAngle)`.
  - Generate the trapezoidal tooth cross-section at each end scaled by its radius; loft corresponding vertices into triangles via `BufferGeometry`.
  - Add hub cylinders at both ends.
- `executeRecipe` dispatches `gear.gearType === "bevel"` → `buildBevelGear`.

### T17 · Backend: worm gear support (schema + sanitize + prompt)
**File:** `backend/gemini.js`

- Extend `sanitizeRecipe` for worm fields (finite, bounded).
- Prompt: add "worm gear" to classification examples; "set gearType 'worm'; provide worm params (leadAngle, pitch, threadRadius, length) and the wheel params (teeth, module, faceWidth, boreRadius)."

### T18 · Frontend: buildWorm + buildWormWheel + assembly
**File:** `frontend/src/lib/recipe.js`

- `HelixCurve` — `THREE.Curve` subclass producing a helix from `{radius, pitch, height}`.

## Notes / risks

- Gemini recipe output quality varies; the sanitizer + fallback-to-parametric path guarantee we never crash or regress known types.
- The `ANALYSIS_SCHEMA` retry path is the silent-bug trap here — whenever recipe fields are added to the prompt/schema, they must be mirrored into `ANALYSIS_SCHEMA` or the retry path loses them.
- **True involute gear teeth** (real curve-fitting, not the trapezoidal approximation) are out of scope for v1 and tracked as a follow-up task.
- Bevel/worm builders are v1 approximations (lofted trapezoid teeth / helix-tube thread), not production machining-accurate geometry.
- **Optional future enhancement (not in scope):** two-pass analysis — call 1 classifies + counts teeth; call 2 estimates module/proportions given that context. More reliable than one-shot, adds latency/cost.
- No new npm dependencies required (three.js stays at `^0.128.0`).
- Later, if true boolean cutouts are needed (drilled radial holes in lathe parts, arbitrary pockets), consider upgrading three.js and adding a CSG library as a separate follow-up — out of scope here.

## Workstream 4 — Manufacturing Intelligence Report (Cost, Process & Lead-Time Engine)

Goal: Turn the analysis ReForge already produces (dimensions, materialEstimate, manufacturingProcess, geometryRecipe) into an actionable cost, process, and lead-time estimate — the "Manufacturing Intelligence" layer. A deterministic calculation engine (no Gemini call) — fast, cheap, reproducible, and debuggable. Gemini classifies; a small curated knowledge base + closed-form formulas do the rest.

**Status:** T20–T26 implemented. T27 verification complete — build passes (`✓ built in 3.08s`, exit code 0), formula chain hand-checked.

### T20 · Backend: manufacturing knowledge base

**File (new):** `backend/manufacturing-data.js`

Exports three plain constant tables (`MATERIALS`, `DEFAULT_MATERIAL`, `PROCESS_RATES`, `OVERHEAD_MARGIN`) with v1 placeholder estimates at approximate India job-shop market levels (INR). All marked clearly as illustrative demo data. Non-subtractive processes (casting, injection molding, forging) use `removalRateCm3PerMin` as a loose "production rate" proxy for v1 time estimation only — commented clearly in the file.

### T21 · Backend: volume/mass estimation

**File (new):** `backend/geometry-volume.js`

Exports `estimateVolumeCm3(analysis)` → `{ volumeCm3, source }` where source is `"recipe"`, `"fallback-dims"`, or `"insufficient-data"`. All internal arithmetic kept in mm³; divided by 1000 at the very end. Also exports `resolveComponentTypeServer(analysis)`.

Volume by recipe style:
- **revolved** — frustum stacking over revolvedProfile `{z, radius}` points (solid revolution)
- **extruded** — shoelace formula for outline polygon, minus hole areas, × depth
- **gear** — coarse cylinder approximation (cost-estimation grade only), mirrors `buildGearFromRecipe()` derivation
- **combination** — sum of standard primitive volume formulas (box/cylinder/sphere/cone/torus)

Fallback: bounding-volume × fill-factor per component type (spur gear 0.72, flange 0.55, bearing 0.45, bracket 0.35, other 0.50). Returns `{ volumeCm3: null, source: "insufficient-data" }` when dimensions are insufficient.

### T22 · Backend: cost / process / lead-time calculation

**File (new):** `backend/manufacturing.js`

Exports `computeManufacturingIntelligence({ analysis, quantity })`.

1. **Material resolution** — substring match against `MATERIALS[i].match` keywords; falls back to `DEFAULT_MATERIAL` (mild steel) with an entry in `assumptions[]`.
2. **Volume & mass** — calls `estimateVolumeCm3`; returns `{ error: "insufficient-data", message }` (not a thrown 500) when geometry is insufficient.
3. **Process recommendation** — deterministic rule tree (plastic vs. metal, revolved vs. non-revolved, quantity thresholds) with a plain-language `reasoning` string naming every decision driver.
4. **Machining time** — `complexityMultiplier = 1 + 0.05 * max(0, featureCount − 3)`; machining hours from setup + volume/rate formula.
5. **Lead time** — base days from machining hours + flat +5 working days for first-time tooling if `toolingCostINR > 0`.
6. **Cost** — material + machining + toolingPerUnit + 20% overhead; output as a range `[×0.85, ×1.25]` to never present false precision.

Output shape includes `volumeCm3`, `massKg`, `material`, `process` (recommended + alternatives + reasoning), `cost` (currency, low, high, breakdown), `leadTime`, `quantity`, `assumptions`.

### T23 · Backend: new API route

**File:** `backend/index.js`

Added `POST /api/manufacturing-intelligence` following the existing try/catch → `res.status(error.status || 500).json({ error })` pattern. `validateAnalysisShape()` re-sanitises `geometryRecipe` via the already-exported `sanitizeRecipe` from `gemini.js` (untrusted client input). `clampQuantity()` enforces `[1, 100 000]` integer clamping. Insufficient-data case returns HTTP 200 with `{ manufacturingIntelligence: { error: "insufficient-data", ... } }` so the frontend displays a graceful state without a network error.
